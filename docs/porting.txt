ANY AGENTIC LOOP
================

orly is a library and a CLI. Claude Code is one adapter, in one file. Nothing in the core
knows what harness it is running under.

  src/client.ts        the only thing here that speaks HTTP
  src/gate.ts          questions and policy
  src/normalize.ts     message log -> Turn
  src/specs.ts         specifiers: validation, question generation, scoring
  src/enrich.ts        evidence the transcript does not contain
  src/enrich-checks.ts the project's own commands as evidence
  src/enrich-context.ts declared sources — a ticket, a deploy — as text for the judge
  src/fingerprint.ts   what the tree looked like when something was computed
  src/evidence.ts      all three, wired the way every host wants them
  src/session.ts       .orly discovery, the key, layering, loop control
  src/log.ts           the verdict log and cut proposals
  src/guard.ts         refusing edits that weaken the gate
  bin/orly.ts          the CLI
  adapters/            one file per host


WHAT A HOST HAS TO DO
---------------------

Four calls. Everything else is the library's problem:

  resolveKey(cwd)                     TYPESAFE_API_KEY, or the keyCommand in .orly
  normalizeLastTurn(messages)         the host's log -> a Turn
  projectEvidence({cwd})              files, checks and declared context, from the root
  judge(turn, {apiKey, specs, enrich})

None of these know what a hook is. Key resolution and evidence wiring used to live in the
Claude Code adapter, so a second host had to reimplement both — and the one that did it
slightly differently disagreed with the first about the same repository.


THE CLI
-------

  echo '{"messages":[...]}' | orly judge

  -> {"block":true,"reason":"...","line":"...","answers":{...},"usage":{...}}

  exit 0  the turn may end
  exit 2  it may not
  exit 1  the gate could not run

`messages` accepts either dialect: Anthropic content blocks (tool_use / tool_result) or
OpenAI chat messages (tool_calls / role:"tool"). The last human message onward is judged.
`{"turn":{...}}` takes a pre-normalised turn for logs that are neither shape.
`orly schema` prints both shapes with a working example. A malformed input exits 1 naming
the bad field, before the key is read and before any request is spent.

  orly schema         print the accepted input shapes and the output shape
  orly watch          run the declared checks on every change, off the critical path
  orly specs [path]   check a spec list is decidable from recorded evidence
  orly fit            propose cuts from the log
  orly ask Q [Q...] [file...] [-]   ask now, between turns


ASKING DIRECTLY
---------------

  orly ask "is the stub gone?" "is there a test for it?" src/thing.ts
  git diff | orly ask "does this touch auth?" "is a test included?" -
  orly ask --json "does this touch auth?" src/auth.ts

Named files become `files` in the state; "-" reads piped text into `input`. Each question
becomes a Noul and prints yes/no with its probability; exit 2 if any came back no.

The gate answers once, at the turn boundary, about everything. This answers immediately,
about one thing — or twenty. Batching is close to free because the state dominates the
cost: measured on one file, 1 question cost $0.00017 and 40 cost $0.00021, with latency
flat at roughly 300-400 ms.

--json gives a program the whole answer: every probability, the cut they were split at,
the latency and the token count. Exit 2 if any answer came back no, either way.

The printed yes/no splits at 0.5 as a reporting convenience. Anything you act on needs a
cut fitted for that question's wording - see notes/calibration.txt. 0.5 is where an unfitted
question looks most trustworthy and is least so. ORLY_ASK_CUT moves the split once you
have fitted one.

The key comes from resolveKey, same as the hook: TYPESAFE_API_KEY, else the keyCommand in
.orly/config.json. Nothing here needs an interactive shell's environment.


THE TURN
--------

  user_request              what the human asked for
  assistant_final_message   the closing message
  assistant_said            everything the agent said this turn, in order
  actions_taken             one line per tool call
  command_results           tool output, failures preserved
  conclusive                did the agent speak after its last action?
  project                   evidence gathered independently (optional)

conclusive is the one that matters for a host reading from a log another process writes.
A turn whose conclusion has not been recorded yet cannot be judged: every "and was it
reported?" question answers no, because the report does not exist yet.


WRITING AN ADAPTER
------------------

Translate the host's turn-end event into a Turn, call judge(), translate the Verdict back.
Everything else is defence, and it all points one way: every error path ends in LET THE
AGENT STOP. No key, unreadable log, timeout, non-2xx, a 200 that is not the documented
shape, a turn whose conclusion never arrived — all of them allow.

A judge that is down must not become a wall.
