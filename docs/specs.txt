WRITING SPECS
=============

A spec is one yes/no question about the recorded evidence of a turn: the commands that
ran, what they printed, what the agent said, and any evidence orly gathered itself.
Nothing else is visible to the judge.


THE TREE
--------

One file per spec; the file name is the id, folders are only for grouping.

  .orly/goal                            `rounds: 6`, a blank line, one goal per line
  .orly/specs/build/tests_green.spec

    cut: 0.52

    Do `command_results` show a test run that reported zero failures, executed after
    the last edit in `actions_taken`?

Optional `key: value` header lines, a blank line, then the question:

  cut         the probability at which it counts as met (default 0.70)
  require     <path> <op> <value>, decided in code instead of by the judge;
              op is equals, lte, gte, present, absent or contains
  evidence    files or context sources to read at judging time, comma separated
  optional    yes: may stay unmet if the agent says why
  gather      what the agent should bring when nothing produces the evidence
  true/false  what met and unmet look like

A file that does not parse becomes a spec that can never be met, so a typo blocks instead
of silently dropping a check. `orly tree` prints the index. Without a tree, a single
.orly/specs.json ({goal, maxRounds, specs: [...]}) is read; one that does not parse blocks the same way.


GOALS
-----

The goal file is a list, most important first. Each line is `- <group>: <text>`, and
the specs under .orly/specs/<group>/ are the ones written against that goal:

  rounds: 6

  - api: retries on every client call
  - readme: the README says each thing once

  orly goal api "retries on every client call"     appends; the file is never overwritten
  orly tasks                                       unmet specs after the last judged turn,
                                                   in goal order

The block names unmet specs in the same order, so several agents working the same tree
all start from the most important open task. A line without a group is a goal no spec
serves yet. Appending a goal keeps the guard's baseline; removing or rewording one
starts a new spec set.


FOUR RULES
----------

1. Ask about what is observable. "Do `command_results` show zero failures?", not "are
   the tests good".
2. Never make the judge simulate execution. It reads text well and predicts runtime
   badly. Ask about a command's output, not about what code would do.
3. No taste words (clean, readable, idiomatic, robust, proper...). They are rejected.
4. If a spec only sometimes applies, branch explicitly: "First check whether
   `actions_taken` contains an edit to X. If there is NO such edit, answer yes. If there
   IS, answer yes only when `command_results` show 0 failures after it." An either/or
   phrasing gets overridden by unrelated failures elsewhere in the turn.


EVIDENCE
--------

A spec about file state must not depend on what the agent chose to print. Name the file,
and orly reads it at judging time into `project.files`:

  impl/no_stub.spec

    evidence: duration.js

    Look at the `duration.js` entry under `project.files`, which is the file's real
    current content. Is the stub gone?

A missing file is recorded as "[file does not exist]".


CHECKS: FACTS DECIDED IN CODE
-----------------------------

A command in .orly/config.json runs at judging time; a `require` spec asserts on it and
never reaches the model:

  "checks": { "tests": { "command": "bun test", "countPattern": "\\bfail\\b" } }

  build/tests_green.spec

    require: checks.tests.exit equals 0

    The test suite exits 0.

Each check records `exit`, `out` (the tail) and, with a countPattern, `matches`. Only
checks some spec reads are run, in parallel. `orly watch` runs them on every change so a
turn never waits.


CONTEXT: TEXT SOMEONE HAS TO READ
---------------------------------

For what a command prints but no exit code decides — a ticket, a deploy status — declare
a context source and name it in `evidence`. Its output goes to the judge under
`project.context`:

  "context": { "ticket": { "command": "jira issue view $TICKET --plain" } }

  ticket/ticket_covered.spec

    evidence: ticket

    Look at `ticket` under `project.context`, which is the issue tracker's own text.
    Does the work recorded in `actions_taken` satisfy every acceptance criterion it lists?

A source that fails is reported as unknown, never as empty.


WHEN NOTHING CAN PRODUCE IT
---------------------------

Name the evidence anyway and say how to get it. The block asks the agent in those words,
and the next turn is judged on what it brought:

  review/reviewed.spec

    evidence: design_review
    gather: Paste the reviewer's verdict, with their name and the date.

    Look at `design_review` under `project`. Did the reviewer approve the approach
    taken in `actions_taken`?


EVERY MISTAKE BECOMES A CASE
----------------------------

Every judged turn is kept in .orly/turns/ with the evidence the judge saw. When one went
wrong, freeze it:

  orly turns                      find it; `last` is the newest
  orly case last block "said tests pass while one failed" \
    --spec build/tests_ran --ask "Do `command_results` show zero failures after the last edit?"
  orly case last pass "blocked a finished README edit"

`block`: it should have been stopped; --spec names the spec that must catch it, --ask
writes that spec if it is new. `pass`: it was blocked wrongly. The case goes to
.orly/cases/ and every case is replayed in the same call.

  orly replay                     every case, live judge, current specs

A case is right only if the verdict matches and the named spec is the one that fired.
Each run is appended to .orly/replay.jsonl, so every change is measured against every
mistake recorded so far.


CHECK AND TUNE
--------------

  orly specs [path]     rejects taste words, then asks the judge whether each spec is
                        decidable from recorded evidence
  orly fit              proposes cuts from the log: blocks followed by real work versus
                        blocks the agent only talked past

When a spec misfires, check in this order: the state the judge received, the wording,
then the cut. Wording moves the probability more than the cut does; after rewording, fit
the cut again with `bun test/spec-fit.ts`.
