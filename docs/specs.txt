WRITING SPECS
=============

A spec is one yes/no question about the recorded evidence of a turn: the commands that
ran, what they printed, what the agent said, and evidence orly gathers itself. Nothing
else is visible to the judge.

Write as many as the project has rules. Every judged spec is one more question in the
same single request. A `require` spec runs a command instead of asking the judge.


THE TREE
--------

One file per spec. The file name is the id; folders only group specs under a goal.

  .orly/goal
  .orly/specs/build/tests_green.spec

    require: checks.tests.exit equals 0

    Does the test suite exit zero?

A file is optional `key: value` header lines, a blank line, then the question:

  cut         probability at which a judged spec is met, between 0 and 1 (default 0.70)
  require     <path> <op> [value], decided in code instead of by the judge. op is one of
              equals, lte, gte, present, absent, contains. The value is parsed as JSON
              when it can be (0, true, "x"), else taken as a bare string
  evidence    files to read at judging time, comma separated (see EVIDENCE)
  optional    yes: the turn may end with this spec unmet
  true        what "met" looks like, replacing the default criterion
  false       what "not met" looks like
  fitted      a note on where the cut came from; not used by the gate
  select      one SELECT or WITH statement over the tables in .orly/tables: a row spec (ROW SPECS)

An unknown header, a cut outside (0, 1) or a file with no question becomes a spec that can
never be met, so a typo blocks every turn instead of silently dropping a check. The same
holds for a .orly/goal file that does not parse.

`orly specs` validates the whole tree and exits 1 when anything is rejected:

  - the id (file name) must be a slug: letters, digits, _ and -
  - ids must be unique across folders
  - `require` must name a path and a known op
  - `require: checks.<name>…` must name a check that .orly/config.json defines
  - the question must be at least 15 characters
  - taste words (clean, readable, idiomatic, robust, proper, …) are rejected in judged
    specs; inside a `code span` they are command text and allowed


GOALS
-----

.orly/goal is a list, most important first. Each line is `- <group>: <text>`, and the
specs under .orly/specs/<group>/ serve that goal:

  rounds: 6

  - api: retries on every client call
  - readme: the README says each thing once

  orly goal api "retries on every client call"     appends; never overwrites
  orly tasks                                       every spec, in goal order

A body with no `- ` lines is read as one goal. `rounds` caps how many times in a row the
gate may block one session (default 6). The gate also stops blocking once no additional
spec has been met for more than 2 rounds, so a stuck agent is handed back to the user
instead of looping. Unmet specs are listed in goal order in the block message.

`orly goal` refuses to append to a goal file that does not parse, rather than drop the
goals already in it.


FOUR RULES
----------

1. Ask about what is observable. "Do `command_results` show zero failures?", not "are
   the tests good".
2. Never make the judge predict runtime behaviour. Ask about a command's output, not
   about what the code would do.
3. No taste words. They are rejected.
4. If a spec only sometimes applies, branch explicitly: "First check whether
   `actions_taken` contains an edit to X. If NOT, answer yes. If it does, answer yes
   only when `command_results` show zero failures after it."


EVIDENCE
--------

A spec about file state must not depend on what the agent chose to print. Name the file
and orly reads it at judging time into `project.files`:

  evidence: duration.js

  Look at the `duration.js` entry under `project.files`, which is the file's real
  current content. Is the `throw new Error("not implemented")` stub gone?

Paths are relative to the project root (the folder holding .orly). Limits:

  - 8 files per turn across all specs; the rest are recorded as not read, which the judge
    must treat as unknown, not absent
  - 12000 characters per file; a longer file is cut and says so
  - a missing file is recorded as "[file does not exist]"
  - a path or symlink that resolves outside the project is not read, because evidence is
    sent to the judge


CHECKS: FACTS DECIDED IN CODE
-----------------------------

A check is a shell command in .orly/config.json that runs at judging time, in the project
root. A `require` spec asserts on its record and never reaches the model:

  "checks": { "tests": { "command": "bun test", "countPattern": "\\bfail\\b" } }

  require: checks.tests.exit equals 0

Each check records:

  exit      the exit status; null when the command could not run or was killed
  out       the last 400 characters of stdout and stderr
  matches   with countPattern, how many times the regex matched the full output

A check is killed, with its child processes, after timeoutMs (60000). Only checks that some
spec names are run, in parallel. Check records are never sent to the judge.

In a git repository a check reruns only when the tree moved: HEAD, `git status`, or the
content of a changed or untracked file. Otherwise the last record is reused, so a turn that
changed nothing decides in milliseconds. A check that reads anything else (a gitignored file,
a service, the clock) must set "live": true to run every time. A killed check is not reused.

A stop waits on checks for ORLY_CHECK_BUDGET_MS (8000). A check still running then keeps
running in the background, its specs are left out of this stop's verdict (the hook says so),
and the next stop reads its result. timeoutMs still kills it.

A `require` that cannot be decided (a missing path, a number compared with a string) is
unmet, never met.


ROW SPECS
---------

A spec with a `select:` header judges records instead of the turn, and never runs at Stop.
.orly/tables maps a table name to a glob, relative to the project or absolute (~ allowed):

  memo: .kern/memos/*/*.md
  bus: .swarm/data/bus.jsonl

Each .md file is a row {path, kind, fm, body, mtime}: fm is the frontmatter as JSON (query
it with fm->>'status'), kind is fm.kind, else the parent folder. Each .jsonl line is a row
with the object as fm and body null. Files are read, never written. Keys are normalized:
targets -> target, asked_by -> askers, asked-at -> asked_at, and a value "883 → 900" also
gives <key>_before and <key>_after as numbers.

  select: SELECT path FROM memo WHERE fm->>'status' = 'claimed'
  require: rows equals 0

  Is any unit still claimed?

`require: rows <op> N` decides by the row count alone, with no judge call. Without it each
row is one yes/no question in one judge request, and the spec fails when any row's
probability is above `cut` (default 0.70). More than 50 rows fail as too broad.
`orly rows <spec-path-or-id>` prints the rows and answers.

WHEN A SPEC MISFIRES
--------------------

Check, in this order: the state the judge received (`orly judge` prints the answers),
the wording, then the cut. Wording moves the probability more than the cut does. Never
lower a cut to make a turn pass; see guard.txt.
