**Your agent says it's done. Something should check.**

orly turns your goal into specifiers and checks every one at the end of every turn — one
request, under a second, six thousandths of a cent. Whatever isn't true goes back to the
agent with the gap named. It keeps working until they hold.

```sh
claude plugin marketplace add /path/to/orly
claude plugin install orly@orly-local
```

Then `/orly:orly <your goal>`.

---

## What you get

**Verification a test suite leaves to you.** Whether the agent ran the tests it says it
ran. Whether a TODO is standing in for the feature you asked for. Whether the third item
of a three-item request was delivered. Whether a number in the summary came from output.

**Judgment on live files.** A spec names the files it depends on; orly reads them itself
at judging time. Same transcript, stub still on disk: `0.07`, blocked. Stub gone: passes.
The verdict follows the code.

**A gate that holds under pressure.** The agent tuning the gate is what the gate judges.
Weakening a cut, dropping a spec or marking one optional is refused by the harness — at
the edit, and again at the turn's end. Tightening stays open.

**Room to run on every turn.** ~850 ms, ~1,600 input tokens, **$0.67 per 10,000 turns**.

**Answers between turns.** `orly ask "is the stub gone?" src/thing.ts` returns in under a
second. Same judge, as many questions at once as you like.

**Improvement that compounds.** Every judgment is logged. Specs and code reload on the
next turn. A cut fitted once is inherited by every project.

## Measured

12 fixtures against live `jev-1.13.0`: **12/12** block-vs-pass, and the "what next?"
question picks the right step **5/5** on blocked turns. Every cut is fitted against real
negative cases. Per-fixture numbers move between runs and live in
[`docs/measured.txt`](docs/measured.txt), regenerated by `bun test/calibrate.ts --write`.

Found in its own development: a refactor shipped without re-verification, a number quoted
from memory, and a fabricated justification — that last one written while documenting the
check that catches it.

## Worth knowing

Deterministic facts belong in code. A `require` spec asserts on exit codes and diagnostic
counts directly, costs no tokens, and reports what it found.

The `coverage` Score is what catches a turn with no work in it: every other question asks
whether something was done wrong, this one asks whether anything was done. Removed, that
failure mode passes 3 runs out of 3.

Every apparent misjudgement in development traced to the state the judge was handed or a
mislabelled fixture. Debug in that order: state, then wording, then the cut. Wording moves
the numbers further than thresholds do.
